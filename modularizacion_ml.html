🚀 Modularización de Proyectos ML

Guía práctica para estudiantes sin experiencia en despliegue

¿Por qué modularizar?

La modularización es la práctica de organizar tu código en carpetas y archivos lógicos. Conforme tu proyecto crece, esto te ayuda a:

  • Encontrar el código fácilmente
  • Reutilizar funciones
  • Trabajar en equipo sin conflictos
  • Hacer el despliegue más sencillo

📚 Nivel 1: Proyecto Mínimo (Sin Despliegue)

Para: Aprendizaje, Experimentos

¿Cuándo usarlo?

Este es el nivel más simple. Perfecto para cuando estás aprendiendo, haciendo pruebas rápidas o trabajando en un notebook de Jupyter. Aquí la organización es mínima pero suficiente.

📋 Explicación de archivos:

notebooks/
Aquí van todos tus Jupyter notebooks (.ipynb)
data/
Carpeta para datos crudos y procesados
requirements.txt
Lista de librerías necesarias (pandas, scikit-learn, etc)
README.md
Explicación del proyecto (qué hace, cómo ejecutarlo)

✨ Ventajas

  • Súper simple
  • Perfecto para empezar
  • Ideal para Jupyter

⚠️ Limitaciones

  • No es escalable
  • Código desordenado
  • Difícil de compartir
💡 Consejo: Usa esto solo si tu proyecto tiene menos de 3 notebooks. Cuando tengas más, sube al siguiente nivel.

💻 Nivel 2: Despliegue Local Simple

Para: Proyectos pequeños, uso local

¿Cuándo usarlo?

Cuando terminas de experimentar y quieres tener un código limpio reutilizable. El modelo se ejecuta en tu máquina, pero el código está bien organizado.

graph TD A["📁 proyecto-ml"] --> B["📁 src"] A --> C["📁 data"] A --> D["📁 notebooks"] A --> E["📁 models"] A --> F["📄 requirements.txt"] A --> G["📄 README.md"] A --> H["📄 main.py"] B --> B1["__init__.py"] B --> B2["preprocessing.py"] B --> B3["model.py"] B --> B4["utils.py"] C --> C1["raw/"] C --> C2["processed/"] D --> D1["01_eda.ipynb"] E --> E1["modelo_entrenado.pkl"]
📁 Estructura de carpetas (tree)
proyecto-ml/ ├── 📁 src/ │ ├── __init__.py │ ├── preprocessing.py │ ├── model.py │ └── utils.py ├── 📊 data/ │ ├── raw/ │ │ └── datos.csv │ └── processed/ │ └── datos_limpios.csv ├── 📦 models/ │ └── modelo_entrenado.pkl ├── 📓 notebooks/ │ └── 01_eda.ipynb ├── main.py ├── requirements.txt ├── README.md └── .gitignore

📋 Estructura recomendada:

src/
Aquí va TODO tu código Python reutilizable
src/preprocessing.py
Funciones para limpiar y preparar datos
src/model.py
Funciones para entrenar y usar el modelo
src/utils.py
Funciones auxiliares que reutilizas
main.py
Script principal que orquesta todo (entrada del programa)
models/
Aquí guardas el modelo entrenado (.pkl, .h5, etc)
💡 Ejemplo de main.py: 
from src.preprocessing import limpiar_datos
from src.model import entrenar_modelo

# 1. Cargar datos
datos = pd.read_csv('data/raw/datos.csv')

# 2. Procesar
datos_limpios = limpiar_datos(datos)

# 3. Entrenar
modelo = entrenar_modelo(datos_limpios)

# 4. Guardar
modelo.save('models/mi_modelo.pkl')

✨ Ventajas

  • Código limpio y organizado
  • Fácil de reutilizar
  • Pasos claros

⚠️ Limitaciones

  • Solo funciona en tu PC
  • No es accesible desde internet
  • No hay interfaz bonita

🔌 Nivel 3: API Local Básica

Para: Pequeños servicios, testeo

¿Cuándo usarlo?

Cuando quieres que otras aplicaciones puedan usar tu modelo. Crearás un servidor que espera peticiones HTTP. Perfecto para testear antes de subir a producción.

graph TD A["📁 proyecto-ml"] --> B["📁 src"] A --> C["📁 data"] A --> D["📁 models"] A --> E["📁 tests"] A --> F["📄 app.py"] A --> G["📄 requirements.txt"] A --> H["📄 README.md"] A --> I["📄 .env"] B --> B1["__init__.py"] B --> B2["preprocessing.py"] B --> B3["model.py"] B --> B4["utils.py"] E --> E1["test_model.py"] E --> E2["test_api.py"] C --> C1["raw/"] C --> C2["processed/"] D --> D1["modelo_entrenado.pkl"]
📁 Estructura de carpetas (tree)
proyecto-ml/ ├── 📁 src/ │ ├── __init__.py │ ├── preprocessing.py │ ├── model.py │ └── utils.py ├── 📊 data/ │ ├── raw/ │ │ └── datos.csv │ └── processed/ │ └── datos_limpios.csv ├── 📦 models/ │ └── modelo_entrenado.pkl ├── ✅ tests/ │ ├── test_model.py │ └── test_api.py ├── app.py ├── requirements.txt ├── .env # No subir a Git! ├── .env.example ├── README.md └── .gitignore

📋 Archivos nuevos/modificados:

app.py
Crea el servidor API (Flask o FastAPI)
tests/
Tests para verificar que todo funciona bien
.env
Variables de configuración (rutas, puertos, etc). NO subir a Git
💡 Ejemplo de app.py con FastAPI: 
from fastapi import FastAPI
from src.model import cargar_modelo

app = FastAPI()
modelo = cargar_modelo('models/mi_modelo.pkl')

@app.get("/")
def home():
    return {"mensaje": "API funcionando"}

@app.post("/predecir")
def predecir(datos: dict):
    resultado = modelo.predict([datos])
    return {"prediccion": resultado}

# Ejecutar: uvicorn app:app --reload

✨ Ventajas

  • Otras apps pueden usarlo
  • Pruebas fáciles
  • Puedes testear antes de producción

⚠️ Limitaciones

  • Solo accesible localmente
  • Se apaga si reinician tu PC
  • No escalable a muchos usuarios

☁️ Nivel 4: Despliegue en la Nube (AWS, GCP, etc)

Para: Producción, múltiples usuarios

¿Cuándo usarlo?

Cuando tu aplicación necesita estar disponible 24/7 para usuarios reales. El código está en un servidor de la nube que es más potente y confiable.

📋 Nuevos componentes:

config/
Configuraciones según el entorno (desarrollo, producción)
config/aws.py
Conexión con servicios AWS (S3, RDS, etc)
scripts/
Scripts de entrenamiento y despliegue automatizados

Especifica cómo empaquetar la app en un contenedor

💡 Arquitectura típica en AWS: 
Cliente HTTP
    ↓
API Gateway (AWS)
    ↓
EC2 / Fargate (Tu API + Modelo)
    ↓
S3 (Datos, Modelos guardados)
RDS (Base de datos)
CloudWatch (Logs y monitoreo)

✨ Ventajas

  • Disponible 24/7
  • Escalable fácilmente
  • Seguridad profesional
  • Monitoreo completo

⚠️ Limitaciones

  • Cuesta dinero
  • Más complejo de configurar
  • Requiere conocimientos DevOps
📚 Servicios AWS que necesitarías:
  • S3: Guardar datos y modelos
  • EC2 o Fargate: Ejecutar tu API
  • RDS: Base de datos si la necesitas
  • CloudWatch: Ver logs y errores
  • SageMaker: (Opcional) Para entrenar modelos a escala

⚡ El flujo natural es progresivo

Inicio del proyecto: Usa Nivel 1, prueba rápidamente con notebooks.

Código validado: Cuando sabes que funciona, sube a Nivel 2 (código limpio).

Testing: Crea tests locales en Nivel 3 (API).

Usuarios reales: Solo entonces ve a Nivel 4 (nube).
